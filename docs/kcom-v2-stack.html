KCOM v2 Stack Options

Two separate choices: how staff edit content (the admin), and what renders the public site. Next.js is ruled out.

1. The admin: three ways to do it

A headless CMS isn't required. With about eight content types and a small editing team, building your own admin is realistic.

ApproachWhat it isStrengthsCosts
Custom admin + own APIYour own API and database, plus an admin app you build, all in the monorepo Fits the devotional workflow exactly (daily scheduling, series, scripture fields). No vendor, no per-seat fees. One codebase, one data model. You build login, roles, rich-text editing, image uploads, drafts and preview yourself. Most effort up front; you own maintenance.
Headless CMSSanity (hosted) or Directus / Strapi (self-hosted) supplies the admin and API Editing UI, media library, roles and drafts ready on day one. Fastest to launch. Content shaped by the CMS's conventions. Hosted plans charge by usage and seats; self-hosted ones need upgrades. Lock-in at migration time.
Traditional CMSWordPress or modern Drupal renders the site and the admin together Familiar to non-technical editors. Huge plugin ecosystem. Doesn't fit the monorepo / TypeScript direction. Plugin upkeep and security patching, which is what got the current site into trouble.
Recommendation: custom admin with a separate API.

The content model is small and stable, and the daily devotional is the core of the site. A purpose-built editor ("write today's capsule", pick a series, paste a scripture reference) will be easier for staff than a generic CMS. The monorepo already has the shared content package, so the API, admin and migration scripts all use the same rules.

Choose a headless CMS instead if launch speed matters more than fit, or if nobody will maintain the code after launch.

2. What the custom route looks like

apps/
  web/        # public site, reads from the API
  admin/      # staff editing app (login required)
  api/        # REST/JSON API: content, media, auth
packages/
  content/    # schemas + types shared by all three
  db/         # database schema and migrations
  ui/  migrate/  config/

Suggested pieces

  • API: Hono (small, fast, TypeScript)
  • Database: PostgreSQL with Drizzle ORM
  • Auth: Better Auth (email login, roles)
  • Rich text: Tiptap editor, stored as JSON
  • Media: S3-compatible storage (Cloudflare R2)
  • Search: Postgres full-text to start

Admin features to build

  • Capsule editor with scripture, decrees and prayer fields
  • Calendar view of scheduled capsules
  • Draft, schedule, publish
  • Series and topic management
  • Pages, blog, books, gallery editors
  • Users and roles (admin, editor)

Monorepo tooling

Two layers: the package manager that links the apps and packages together, and a task runner that builds, tests and caches across them. The repo is small: 3 apps and about 5 packages.

OptionWhat it isStrengthsCosts
pnpm workspaces alonePackage manager with built-in workspace commands (pnpm -r, --filter)Nothing extra to learn. Strict dependencies, fast installs, shared version "catalogs".No build caching; every build and test runs from scratch.
pnpm + TurborepoTask runner layered on pnpm; one small turbo.jsonCaches builds and tests, runs only what changed, runs tasks in parallel. Can be added or removed in an afternoon. Large community.Owned by Vercel; its free remote cache is on Vercel (optional, can self-host or skip).
NxFull monorepo platform: task runner, code generators, project graph, pluginsVery capable; "affected" builds, generators for new apps and packages.Heavier and more opinionated; more config and concepts than this repo needs.
RushMicrosoft's monorepo manager, built for large enterprise repos (uses pnpm underneath)Very strict dependency rules, versioning and publishing policies, build cache.Built for hundreds of packages and big teams. Its own CLI and config (rush.json, common/config), smaller community, slower to set up. Overkill here.
moonRust-based task runner that also manages tool versionsFast, language-agnostic.Smaller community and fewer examples.
Recommendation: pnpm workspaces with Turborepo.

Caching and "only rebuild what changed" pay off in CI and Cloud Run deploys, with very little setup. Rush's strengths (publishing many packages, strict policies for large teams) don't apply to a 3-app ministry site. If you'd rather keep things minimal, pnpm workspaces alone works; Turborepo can be added later without restructuring.

3. The public site framework

FrameworkGood atWatch out forFit
AstroContent-heavy sites. Ships almost no JavaScript, so pages are very fast. Can pre-build all ~900 capsule pages or render on demand.Less suited to app-like interactivity, but the public site barely needs any.Best for web
SvelteKitFast, simple full-stack framework. Good for both the site and an admin app.Smaller ecosystem than React.Strong; also suits admin
React Router (Remix)Solid data loading and forms. Large React ecosystem.More JavaScript on public pages than Astro.Better for admin
NuxtVue's full-stack framework, very capable.Adds Vue to the team's skill set if you're React-leaning.Fine if you like Vue
Suggested combination:

Astro for the public site, a React (Vite) or SvelteKit app for the admin, and Hono for the API. Pick React or Svelte for the admin based on what you're more comfortable maintaining.
