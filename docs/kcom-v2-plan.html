KCOM v2 Rebuild Plan

How the content of the current site maps to a new build, and how about 873 Capstone Capsules move over without losing a single page or link.

Current: Drupal 7 (unsupported) ~873 daily capsules ~10 blog posts Monorepo

Repository layout

One repository with pnpm workspaces and Turborepo. The shared content package defines the content model once; the website, the editing app and the migration scripts all use it, so the imported data is checked against the same rules the site relies on.

kcom-v2/
  apps/
    web/        # public site (framework still open)
    cms/        # editing app for staff (CMS still open)
  packages/
    content/    # content model + types, shared by everything
    ui/         # shared components and design tokens
    migrate/    # Drupal export → transform → import scripts
    config/     # shared lint, TypeScript and formatting settings
  docs/

Migration plan

  1. Get the data. Ideally a database dump of the Drupal site plus its uploaded files folder. If that isn't available, the scripts can crawl the monthly archive pages instead.
  2. Extract. Read every capsule, blog post, page and image into raw files, one per item.
  3. Transform. Split each capsule into scripture, body, decrees and prayer using its labels; detect series from numbered titles; turn images embedded in the text into real image files; clean up old HTML.
  4. Validate. Check every item against the content model and list anything that didn't parse cleanly.
  5. Review. Read about 50 sample capsules plus every flagged item by hand.
  6. Import into the CMS. The import can be re-run safely; it updates items by their old node ID instead of duplicating them.
  7. Redirects. Every old address (/content/…, /blog/…, /archive/YYYYMM, /daily-digest, /rss.xml) gets a permanent redirect to its new page.
  8. Final sync and launch. Pause posting on the old site, import anything new, then switch the domain.
  9. After launch. Watch for missing pages, add redirects as needed, and submit the new sitemap to Google.

Decided

Monorepo toolingpnpm workspaces + Turborepo (Rush, Nx and moon considered; overkill for 3 apps)
Public siteAstro
AdminCustom app: React + Vite (no headless CMS)
APIHono (TypeScript), in the monorepo
Images and filesCloudinary
DatabasePostgreSQL on Neon (free plan), with our own nightly backup; standard Postgres driver so we can move hosts
HostingGoogle Cloud Run for the site, API and admin (deployed like CGHSR), behind Cloudflare's free proxy for DNS, caching and fewer cold starts
Old site dataDrupal database export plus the uploaded-files folder from the current host
Domain and DNSWe have registrar access to kingdomcapstone.org; DNS moves to Cloudflare at launch
MonitoringSentry for errors and PostHog for analytics (reused from CGHSR); free uptime checks; Cloud Run logs; Neon usage alert; backup-failure emails
Public accounts and commentsDropped. Only admin staff log in; visitor accounts are not migrated
Email signupsCollected from launch: double opt-in form, stored in our own subscribers table, Turnstile spam protection, one-click unsubscribe, admin list and CSV export
SearchPagefind for public search (built at site build, runs in the browser, search as you type). Postgres full-text inside the admin. Every search input is debounced (300–500 ms, tuned during testing), public and admin.
Admin rolesAdmin and Editor at launch. Code checks permissions (e.g. capsule:publish, user:manage), never role names; roles are just named sets of permissions, so new roles are a config change.
BrandingKeep the current logo. "Still Waters, with Old Gold": deep water blue, sage, mist, old gold accents, sandstone highlights. Cormorant Garamond titles, Nunito Sans body, Lora italic scripture.
AnimationGentle and purposeful. CSS for hovers and focus; Astro view transitions for page changes; Motion (standalone) for scroll and entrance effects on the site; Motion for React in the admin. Respect reduced motion, soft 300–600 ms easing, animate only position and opacity, never hide text waiting for an animation.
LoginBetter Auth, self-hosted inside the Hono API (not Neon's managed auth)
Page editingAutomatic templates for capsules and lists; homepage and pages built from predefined sections
